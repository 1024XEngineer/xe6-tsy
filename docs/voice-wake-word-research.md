# 中文语音唤醒词调研

目标场景：用户说“**小灵，帮我切换为中日传译**”，只有确认“小灵”是唤醒词后，才解析并执行后半句命令。

## 结论先行

当前 Web 前端没有一个可以直接通过浏览器 JavaScript 调用、同时支持中文自定义唤醒词和离线运行的国内厂商 SDK。阿里云、百度语音、科大讯飞的成熟唤醒能力主要是 Android/iOS 或设备端 SDK；腾讯云的 WebSocket 实时识别可以在浏览器使用，但它是连续 ASR，不是本地唤醒词引擎。

因此推荐采用两级状态机：

1. `DORMANT`：浏览器持续采集低采样率音频，只送本地 VAD/关键词模型，不启动完整翻译链路。
2. `WAKE_CONFIRMED`：检测到“小灵”后进入 5 秒命令窗口，复用现有实时 ASR 的 final 文本。
3. 先用本地规则解析“切换为中日传译 / 开启单向 / 切换双向 / 停止”；未命中时再请求结构化 LLM intent。
4. 命令执行成功后回到 `DORMANT`，避免每个普通句子都被当成控制指令。

## 国内方案对比

| 方案 | 浏览器本地 JS/WASM | 中文自定义唤醒词 | 网络 | 适合当前项目 |
| --- | --- | --- | --- | --- |
| 阿里云智能语音交互语音唤醒 | 否，官方能力以 Android/iOS/设备端 SDK 为主 | 支持，需按产品流程训练/配置 | 端上可离线唤醒，云端命令识别需联网 | 若将 Web 封装成 Electron/Tauri，可优先评估 |
| 百度语音唤醒 | 否，主要是 Android/iOS SDK | 支持，取决于 SDK/唤醒词资源 | SDK 形态决定 | 适合原生壳，不适合纯浏览器 |
| 科大讯飞语音唤醒 | 否，MSC/移动端 SDK | 支持自定义唤醒词或定制模型，通常需要申请资源 | 可做端上唤醒 | 适合原生壳，不适合纯浏览器 |
| 腾讯云实时语音识别 WebSocket | 是，可由 WebAudio/MediaRecorder 连接 | 不是唤醒引擎；可做关键词匹配或热词增强 | 需要联网，音频上传云端 | 可作命令识别，不建议作持续唤醒 |
| 浏览器 Web Speech API | 浏览器 API，不保证本地 | 不支持可靠自定义唤醒词 | 实现和浏览器有关，常依赖联网 | 仅适合原型验证 |

## 对 demo 的对应关系

`demo/lingow-voice-demo` 现在是“VAD 分句 -> 云 ASR -> 规范化字符串精确匹配 -> LLM 兜底”，并没有真正的本地唤醒词检测。它的 `_match_voice_command()` 只在整句文本等于固定短语时命中，所以“小灵，帮我切换为中日传译”需要先增加唤醒词切分，再把剩余文本交给命令解析器。

## 建议的 Web 落地顺序

1. 先实现纯代码的低成本版本：WebAudio + VAD，命令只在用户点击“语音控制”后监听；识别到唤醒词后复用现有 ASR。
2. 需要免点击常驻时，再评估 `sherpa-onnx-web` 或 Vosk 的中文小模型放入 Worker/WASM。它们不是国内云厂商方案，但可以提供浏览器离线运行时；需实测包体、内存和移动端功耗。
3. 如果产品要原生级低误唤醒率，使用 Electron/Tauri 壳接入阿里云、百度或讯飞的原生唤醒 SDK，浏览器层只接收 `wake` 事件和命令文本。

不建议把完整云 ASR 常驻作为正式唤醒方案：它会持续上传环境音频，网络断开时不可用，也无法把“唤醒”和“命令”做出清晰的权限边界。
