# 项目前后端统一开发规范

更新时间：2026-07-15

## 1. 目的与适用范围

本文是 xe6-tsy 的仓库级工程基线，适用于 Go/Gin API、Wails 桌面壳、Vue 3 +
TypeScript 前端、共享契约、测试、文档和 CI。它把 Issue #43 的后端测试约定、
XEngineer 营的软件工程规范，以及本项目已经确定的架构边界转换为同一套可执行规则。

规则优先级从高到低为：

1. 用户对当前任务的最新明确指令；
2. 已接受的项目决策、Proposal 和关联 Issue 验收标准；
3. 本规范和 `AGENTS.md`；
4. 仍在讨论的 Proposal、建议和示例。

Proposal 中的示例用于说明行为，不等于允许提前实现未被接受的范围。规则发生冲突时，
应保留已有行为、缩小改动面并记录冲突，不得自行扩大产品或架构范围。

## 2. 训练营规范在本项目的落地

### 2.1 先设计，再开发

较大需求先在 Issue 中形成 Proposal/Design，至少说明：

- 动机、真实用户和要解决的问题；
- 本期范围以及明确不做的内容；
- 备选方案、选择和理由；
- 受影响模块、数据结构、接口契约和风险；
- 可自动验证或可重复演示的验收标准。

有界面功能先形成文字决策，再形成原型或可交互 Demo。进入编码后，原工程设计成为只读
基线；需求变化以新 Issue、Proposal 或 delta 记录原因和影响，不覆盖旧决策。

### 2.2 Issue 驱动的小步交付

标准链路为：

```text
Proposal -> Design(Issue) -> Coding(PR) -> Review -> Merge -> Release
```

- Milestone 管目标，Issue 管任务与工程设计，PR 管代码与 Review，Release 管可交付版本。
- Issue 必须背景清楚、目标明确、范围可控、验收标准可执行，禁止“优化一下”等空泛任务。
- 一个 Issue 对应一个或少量 PR。PR 必须关联 Issue，不夹带无关功能、重构或格式化噪声。
- PR 保持小而频繁；合入前必须通过必要验证、AI 代码质量检查和人工 Review。
- 每个 Milestone 形成可打 tag 的版本，Release 说明列出功能、验证结果和已知问题。
- Codex 不创建目标为 `main` 的 PR，不合并或直接推送 `main`；默认交付分支为 `dev`，
  除非用户明确指定其他非 `main` 分支。

### 2.3 代码即架构

架构必须通过真实、可编译、可测试的代码表达：

- Go 使用 package、interface、struct、明确的依赖装配和真实模块调用表达边界；
- 前后端使用共享 schema、生成类型和类 SDK 的 service 层表达边界；
- 模块内部允许 fake/stub，但接口、关键数据模型和模块间串联必须真实存在；
- 目录罗列、技术栈清单、没有调用关系的占位代码不能作为架构交付；
- 每个 Milestone 记录相对上一轮的架构变化及原因，避免无依据地反复推翻主干。

## 3. 项目架构与所有权

### 3.1 固定目录

| 内容 | 位置 | 所有权与约束 |
| --- | --- | --- |
| Gin API | `apps/api` | 唯一后端进程入口和权威业务状态 |
| 七个业务模块 | `apps/api/internal/modules` | 模块化单体的领域边界，不拆成七个微服务 |
| Wails 桌面壳 | `apps/desktop` | 窗口、系统权限、麦克风等设备能力 |
| Vue 前端 | `apps/desktop/frontend` | 展示与交互，不拥有后端权威业务状态 |
| 跨端契约 | `packages/contracts` | OpenAPI/JSON Schema、生成客户端和类型的唯一来源 |
| 部署配置 | `deployments` | 不包含密钥和环境私有值 |
| 工程脚本 | `scripts` | 自动化命令，不承载业务逻辑 |

### 3.2 稳定业务边界

- 项目服务于基层政务窗口工作人员；不得扩展成群众端 App、自动审批、行政决定或开放式
  自主 Agent。
- 身份与机构配置、接待会话、转写、事项、知识、记录七个模块各自拥有状态；调用方只通过
  已定义接口或 contract 协作，不跨模块直接修改内部状态。
- ASR、模型、RAG、TTS 和其他供应商能力只能经后端 provider port 接入。前端和桌面壳
  不保存供应商密钥，不直接绑定供应商协议。
- 模型结果只能形成候选或草稿。政策材料需有来源与版本，咨询记录须经工作人员最终复核。
- 默认不保存原始音频，不建立持久声纹，不使用真实群众数据做开发或自动化测试。

## 4. 前后端统一契约

### 4.1 单一事实来源

- HTTP API 统一位于 `/api/v1`；健康检查等运维端点可位于版本组之外。
- 请求、响应、错误、枚举和事件 schema 统一放在 `packages/contracts`。
- TypeScript API 类型和客户端由 contract 生成或从 contract 导出，不在前端复制。
- 生成文件必须标明来源并由命令重新生成，禁止手工修改。
- contract 变更必须在同一个交付中验证 schema、生成物、后端实现和前端消费者。

### 4.2 兼容与错误

- 新增字段优先采用向后兼容方式；删除、改名、改变类型或语义必须经过明确设计与迁移说明。
- API 错误应使用稳定机器码和面向用户的安全信息；不得把堆栈、SQL、密钥、供应商响应或
  敏感正文直接返回前端。
- 时间、ID、分页、空值和枚举语义必须在 contract 中明确，不由前后端分别猜测。
- 前端只通过 `src/services` 中的业务语义 API/Wails bridge 访问后端或设备能力；页面、
  component、store 中不得散落裸 HTTP/Wails 调用。

## 5. Go/Gin 后端规范

### 5.1 分层职责

- Handler 负责路由、鉴权上下文提取、请求绑定/校验、状态码和响应序列化，不承载业务规则。
- service/domain 负责业务规则，不依赖 Gin 类型。
- repository/provider 负责数据库、Redis、MQ、文件或第三方服务，并通过最小接口注入。
- interface 应定义在使用方需要的边界，保持小而具体；不为可能的未来实现制造抽象。
- `context.Context` 沿调用链传递；不得存进 struct，也不得用 `context.Background()` 绕过
  请求取消和超时。
- 错误在有处理意义的边界包装，保留原因；日志不得重复打印同一错误或泄漏敏感数据。

### 5.2 命名与格式

- 测试文件与被测文件放在同一 package 目录，使用 `*_test.go`。
- 测试命名使用 `Test函数名`、`Test类型名_方法名`；基准测试使用 `Benchmark函数名`。
- 所有 Go 文件必须通过 `gofmt`；新增代码应通过 `go vet`、测试、race test 和 build。

## 6. Issue #43：Go/Gin 统一测试规范

### 6.1 测试分层

| 类型 | 验证内容 | 外部服务 | 默认命令 |
| --- | --- | --- | --- |
| 单元测试 | domain、service、工具函数和业务分支 | 否 | `go test ./...` |
| Handler 测试 | 路由、输入、状态码、响应 JSON、依赖交互 | 否 | `go test ./...` |
| 集成测试 | 数据库、Redis、MQ、文件系统或第三方适配 | 是 | `go test -tags=integration ./...` |

业务规则优先由 service/domain 单元测试覆盖，不能只通过 HTTP 间接测试。Handler 测试只
验证 HTTP 边界，不重复 service 的全部业务组合。

### 6.2 测试写法

- 默认使用标准库 `testing` 和 `net/http/httptest`。
- 多个场景使用 `tests := []struct { ... }{}` 表格驱动，每项必须有描述行为的 `name`，
  并用 `t.Run` 执行。
- 失败使用 `t.Fatalf` 或 `t.Errorf`，信息包含 got、want 和定位问题所需的最小上下文。
- 测试 helper 必须调用 `t.Helper()`；只提取确实重复且能提升可读性的初始化。
- Gin 使用 test mode、`httptest.NewRequest` 和 `httptest.NewRecorder`，以 `http.Handler`
  形式执行请求。
- JSON 比较优先反序列化后比较结构或字段；只有格式本身是 contract 时才比较原始字符串。

### 6.3 依赖隔离与确定性

- 单元和 Handler 测试不得连接真实数据库、Redis、MQ、云服务或供应商 API。
- 优先使用贴近使用方接口的手写 fake/stub，并显式验证关键入参和调用次数；不默认引入复杂
  mock 框架。
- 集成测试文件必须声明 `//go:build integration`，且测试数据、启动条件和清理方式明确。
- 不用 `time.Sleep` 等待 goroutine；使用 channel、context、WaitGroup 或可控时钟。
- 测试不得依赖执行顺序、个人机器状态、真实网络、未固定的当前时间或随机结果。
- 新功能覆盖成功、边界和常见失败；缺陷修复先用回归测试证明问题，再修复实现。

## 7. Vue/TypeScript 前端规范

### 7.1 目录与依赖方向

- `app`：启动、路由、全局 provider；`pages`：路由级组合；`features`：按业务能力组织；
  `components`：跨功能、无业务状态的复用组件。
- `services`：API、Wails bridge 和事件客户端；`stores`：跨页面展示/交互状态；`types`：
  仅前端内部类型；`styles`：tokens、主题与全局样式。
- `features` 可依赖 `components`、`services`、`stores`；共享层不得反向依赖具体 feature。
- 页面负责组合，不复制 service、store 或 feature 中已经存在的业务逻辑。

### 7.2 类型、状态和交互

- 启用并保持 TypeScript 严格检查；不得用 `any`、非空断言或类型强转掩盖 contract 问题。
  确需例外时限制在最小边界并说明运行时校验依据。
- 后端权威状态保留在 API；前端 store 只保存必要的会话展示、交互和缓存状态，不创建第二套
  事项、知识或记录状态机。
- 所有异步界面必须处理 loading、empty、success、validation error、dependency error 和
  retry/cancel 中适用的状态，不得只实现成功路径。
- 工作人员的最终确认必须是明确操作；低置信、无来源、stale 或 provider 失败结果不得以
  已确认状态呈现。
- 可访问性使用语义化元素、可见焦点、键盘操作和可关联 label；状态不能只靠颜色表达。

### 7.3 前端测试分层

| 类型 | 验证内容 | 隔离边界 |
| --- | --- | --- |
| 单元测试 | 纯函数、composable、store 状态转换 | 不挂载真实后端或设备 |
| 组件测试 | 渲染、输入、事件、错误和可访问交互 | fake service/bridge |
| E2E | 少量关键工作人员主流程 | 受控 fixture/fake provider |

- 优先测试用户可观察行为，不测试 Vue 内部实现细节或脆弱 DOM 层级。
- service/bridge 在单元和组件测试中使用 typed fake；不连接真实 API、麦克风或供应商。
- 关键流程 E2E 放在 `apps/desktop/frontend/tests/e2e`，覆盖主要成功路径和一个关键失败/降级
  路径；测试结束清理产生的数据。
- 修复缺陷时补回归测试；视觉变化同时检查常用桌面尺寸、窄窗口、长文本和错误状态。
- 当前仓库尚未安装前端工具链。引入时必须在 package scripts 中提供 format、lint、
  typecheck、unit test 和 build 命令，并在 CI/统一检查入口中调用；测试库选择需单独 Issue，
  不由本规范擅自增加依赖。

## 8. 安全、隐私与可观测性

- 仓库、fixture、日志、截图和 Issue 中只使用合成或脱敏数据，不放真实群众信息、音频、
  token、密钥、证件号和联系方式。
- 日志记录事件、request/correlation ID、结果状态和必要耗时，不记录完整转写、提示词、
  政策查询正文或供应商原始响应。
- 外部调用必须有超时、取消、失败降级和可测试边界；失败不得绕过权限、来源或人工复核门禁。
- 配置从环境或受控配置入口读取；示例只提交无敏感值模板。
- 原始音频、转写、候选、引用、咨询记录和日志是不同数据类型，应分别定义最短必要留存、
  访问和删除策略。

## 9. Definition of Done

每个代码交付至少满足：

- 实现与关联 Issue 的范围、明确不做和验收标准一致；
- 模块所有权与依赖方向未被绕过，contract 变化已同步所有消费者；
- 新逻辑或缺陷修复有对应测试，成功、边界和主要失败路径已覆盖；
- 未引入真实外部服务依赖、敏感数据、密钥、无来源政策内容或自动审批行为；
- 文档只更新与本次行为有关的用户入口、运行方式或稳定工程规则；
- 变更可由作者解释，验证结果可重复，已知风险明确记录。

当前 Go 基线命令：

```bash
make check
```

它应覆盖格式检查、`go vet`、单元/Handler 测试、race test 和 build。需要真实基础设施的
集成测试由具备明确环境的流程单独执行：

```bash
go test -tags=integration ./...
```

前端工具链引入后，统一检查入口还必须调用仓库 package scripts 中的 format、lint、
typecheck、unit test 和 build；影响关键桌面流程时再运行 E2E。禁止通过删除、跳过、弱化
测试或降低类型检查等级来让门禁通过。
