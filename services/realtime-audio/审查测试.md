# realtime-audio 审查与测试清单

本清单用于成员 3 的每个 PR。目标不是只证明正常路径可用，而是同时验证错误传播、取消、资源释放、重试和持久化状态能够闭环。

## 1. 范围与基线

- [ ] 执行 `git fetch upstream --prune`，记录 `HEAD`、`upstream/dev` 和当前分支。
- [ ] 执行 `git status --short --branch`，确认没有误带 `go.work.sum`、`.env`、API key、superpower 文件夹或其他实验产物。
- [ ] 执行 `git diff --stat upstream/dev...HEAD` 和 `git diff upstream/dev...HEAD -- services/realtime-audio packages/contracts`。
- [ ] 确认 PR 只修改成员 3 的边界；不修改其他成员的业务实现和数据库。
- [ ] 若修改 `packages/contracts`，先确认 RuntimeSnapshot、RuntimeState、错误码、FinalTurn 和 UsageFact 共识已经冻结。
- [ ] 确认 ConnectionState 与 processing RuntimeState 始终分离。
- [ ] 每个 commit 增删行少于 500 行，PR 总增删行不超过 2000 行。

建议记录命令输出：

```powershell
git rev-parse HEAD
git rev-parse upstream/dev
git status --short --branch
git diff --stat upstream/dev...HEAD
git diff --check
```

## 2. 云端 PR 审查

### 2.1 PR 元数据和 CI

```powershell
gh pr view <PR号> --repo 1024XEngineer/xe6-tsy `
  --json url,state,isDraft,reviewDecision,mergeStateStatus,baseRefName,headRefName,headRepository,statusCheckRollup
gh pr checks <PR号> --repo 1024XEngineer/xe6-tsy
gh pr diff <PR号> --repo 1024XEngineer/xe6-tsy --name-only
```

- [ ] base 必须是最新 `dev`，不能使用未合并 PR 分支作为公共 base。
- [ ] 识别 head 是否来自 fork。跨仓库 PR 不能只按本地仓库名推断 review thread。
- [ ] 检查 `mergeStateStatus`、CI、Review Required 和冲突状态。
- [ ] 已发布分支不 rebase 或 force push，除非成员 3 明确授权。

### 2.2 完整读取 review thread

普通 conversation comment 不能替代 inline review thread。必须读取 `reviewThreads`，至少检查：

- `isResolved`：未解决线程才进入待办；
- `isOutdated`：过期评论仍需确认问题是否已被后续代码实际消除；
- `path`、`line`、`originalLine`：定位当前代码和原始评论位置；
- thread 内所有评论：避免只看到首条意见，漏掉追问或修正。

GraphQL 查询模板：

```powershell
gh api graphql `
  -f owner=1024XEngineer -f name=xe6-tsy -F number=<PR号> `
  -f query='query($owner:String!,$name:String!,$number:Int!){repository(owner:$owner,name:$name){pullRequest(number:$number){reviewThreads(first:100){nodes{isResolved isOutdated path line originalLine comments(first:20){nodes{author{login} body url createdAt}}}}}}}'
```

每个未解决问题必须形成以下闭环：

1. 用代码路径或测试复现评论描述的行为。
2. 判断是否属于本 PR 和成员 3 边界，并标注严重级别。
3. 修改代码，同时新增能在修复前失败的回归测试。
4. 重跑相关包、全模块测试和静态检查。
5. 推送后重新读取 thread 和 CI，确认新 head 已生效。

除非明确授权，不主动回复、resolve review thread 或提交 GitHub review。

## 3. 最新 base 与冲突检查

```powershell
git merge-base HEAD upstream/dev
git merge-tree (git merge-base HEAD upstream/dev) HEAD upstream/dev
```

- [ ] 检查输出中的 `<<<<<<<`、`changed in both` 和同一路径双边修改。
- [ ] 即使 Git 没有文本冲突，也要检查接口、构造函数、状态枚举和依赖装配的语义冲突。
- [ ] 对最新 `upstream/dev` 运行本模块测试，区分本 PR 回归与上游已有失败。

## 4. 本地代码审查

### 4.1 数据和所有权不变量

- [ ] `turn_id` 和 `sequence_no` 只由成员 3 生成，重试不会生成重复或倒退序号。
- [ ] 每个 Turn 只读取一次语言配置快照，后续阶段沿用同一版本。
- [ ] ASR partial 不触发翻译、TTS、FinalTurn 或 UsageFact。
- [ ] 一个 Turn 的 ASR final 只处理一次；重复 final 必须拒绝或去重。
- [ ] FinalTurn 和 UsageFact 只有被可靠 Sink 接受后才算成功。
- [ ] Sink 已接受后的下游失败不会重新执行同一 final，避免重复计费或重复消息。
- [ ] Qwen 翻译模型保持 `qwen3.6-flash`，不引入 DeepSeek。

### 4.2 生命周期和状态矩阵

至少逐项检查下列路径：

| 场景 | 必须满足 |
| --- | --- |
| Start 成功 | 先准备资源，再持久化 Listening，最后 Activate |
| Start 重复 | 不重复打开 source 或启动 worker |
| Start 中途失败 | 清理已拥有资源，持久化 Failed，并允许安全重试 |
| Pipeline terminal error | 持久化 RuntimeFailed，清空 turn/playback，移除 entry，允许重新 Start |
| Stop cancellation | 不误报 RuntimeFailed，不把正常取消当作处理错误 |
| Stop 与失败并发 | 不死锁；Stopping/Stopped 优先于异步失败上报 |
| Stop 超时 | 调用有界，后续重试能够完成清理 |
| source Close 失败 | 错误可见，且不会重复 Close |
| 多 session 并发 | 一个 session 的打开、关闭或失败不阻塞其他 session |

检查 worker 退出时，不仅断言返回错误，还要断言：

- 持久化的 RuntimeSnapshot 最终状态；
- `CurrentTurnID` 和 `CurrentPlaybackID` 是否清空；
- 内存 entry 是否释放；
- 后续 Start 是否真的重新打开资源；
- 失败上报是否只发生一次；
- 取消与真实错误是否被正确区分。

### 4.3 资源、并发与阻塞

- [ ] 所有 goroutine 都有退出条件，channel 发送不会因无人接收永久阻塞。
- [ ] WebSocket、WebRTC track、ASR/TTS stream 和 source 的关闭是幂等的。
- [ ] 不在持有共享 mutex 时执行网络、数据库、Provider、Sink 或可能阻塞的 Close。
- [ ] context 取消能穿透读取、Provider、Sink 和失败上报。
- [ ] 独立 cleanup context 有明确超时，不无限等待。
- [ ] 错误路径同样释放 source、stream、timer 和 goroutine。

## 5. 测试命令

在 `services/realtime-audio` 下执行：

```powershell
go test ./... -count=1 -timeout=60s
go test -tags=integration ./... -count=1 -timeout=120s
go vet ./...
git diff --check
```

针对本次修改的并发或失败路径重复运行：

```powershell
go test ./runtime ./session -count=20 -timeout=60s
go test ./runtime ./session -run 'Failure|Stop|Cancel|Retry|Concurrent' -count=50 -timeout=60s
```

环境支持时执行竞态检测；若工具链阻断，必须原样记录，不能写成通过：

```powershell
go test -race ./... -count=1 -timeout=120s
```

安全检查：

```powershell
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
git grep -n -I -E 'API_KEY=|SECRET=|BEGIN (RSA|OPENSSH|EC) PRIVATE KEY' -- '*.go' '*.yaml' '*.yml' '*.json' '*.toml'
```

- [ ] 默认测试只用 fake，真实 Qwen、Pion 和数据库仅运行隔离集成测试。
- [ ] 检查 URL、代理、重定向和 Host allowlist，防止 SSRF。
- [ ] 检查 WebSocket 并发写、关闭竞态、空音频和无限缓冲。
- [ ] 检查依赖漏洞结果是否为 reachable；记录 Go 工具链版本。

## 6. 提交前自审

```powershell
git status --short
git diff --check
git diff --stat upstream/dev...HEAD
git diff upstream/dev...HEAD
git log --oneline upstream/dev..HEAD
```

- [ ] 从调用者视角重新阅读 public API、错误语义和注释。
- [ ] 从失败注入视角检查每个外部调用：读、写、Close、timeout、cancel。
- [ ] 从并发视角检查锁顺序、等待关系、goroutine 生命周期和重复调用。
- [ ] 从重试视角检查第一次失败留下的状态是否会阻止第二次成功。
- [ ] 从最新 `upstream/dev` 视角检查冲突和上游接口变化。
- [ ] 文档、测试和实现描述同一行为，不用测试绕过真实缺陷。

## 7. 本次漏检的原因与改进

此前审查偏重 happy path、幂等 Start/Stop 和资源 Close，没有主动注入 ASR、翻译、TTS、Sink、音频读取等 terminal error，也没有在 worker 退出后同时验证“持久化状态、entry 清理、再次 Start”三个结果。因此，`Run` 返回错误但 RuntimeSnapshot 仍停在 Listening 的问题没有被本地测试暴露。

后续每个 PR 必须执行两层审查：第一层按正常业务链路验证功能，第二层按上表对每个外部边界注入失败，并验证状态、资源和重试闭环。云端评论必须先在本地复现，再用回归测试证明修复，而不是只针对评论所在行做局部修改。
